INSTALLATION — MODULE 3.1.0-fork2 — 22 OCTOBRE 2026

CVE VISÉES
CVE-2026-109618 : corruption mémoire lors d’un manque de mémoire (OOM).
CVE-2026-109619 : état global périmé entre requêtes, use-after-free possible.
Le module essaie de réduire certains chemins de ces deux CVE. Il ne certifie
pas le correctif complet du moteur PHP. Voir README.md et AUDIT.txt.

PRÉREQUIS ET PORTÉE
Profil : Linux, PHP 7.3.x ou 7.4.33 NTS non-debug, Apache mod_php/prefork.
La version fork2 est testée sur 7.3.33 et 7.4.33 dans Debian 10 ; fork1 avait
aussi été testé sur 7.4.33/Debian 11. Ces essais ne reproduisent pas
vos paquets fournisseur ni votre application. Tester sur clone d’abord.
Python >= 3.7, GCC, make, autoconf, binutils et outils/en-têtes correspondant exactement au PHP installé.
Ne pas mélanger des dépôts ou migrer PHP pour obtenir les en-têtes manquants.
L’installateur ne lance ni APT ni compilation sous root. Il ne touche qu’à
Apache ; un pool FPM actif de la branche ciblée est refusé.

CHOISIR LA BRANCHE
PHP 7.3 : build_php73.py / install_php73.py, CLI /usr/bin/php7.3,
INI /etc/php/7.3/apache2/conf.d/99-hp-guard.ini, API 20180731.
PHP 7.4 : build_php74.py / install_php74.py, CLI /usr/bin/php7.4,
INI /etc/php/7.4/apache2/conf.d/99-hp-guard.ini, API 20190902.
Garder le checkout complet : les scripts partagent des contrôles communs.
PHP 7.3.x est accepté avec correspondance exacte des versions (suffixe fournisseur
compris) entre outils, CLI et Apache ; seuls les essais sur 7.3.33 sont rapportés.
Tester votre version fournisseur sur clone. Aucun binaire d’une autre branche.

PARCOURS PHP 7.3
En compte non root :
    python3 tools/build_php73.py --php /usr/bin/php7.3 --phpize /usr/bin/phpize7.3 --php-config /usr/bin/php-config7.3 --output /var/tmp/hp-guard-build73
Plan sans modification :
    python3 tools/install_php73.py install --build /var/tmp/hp-guard-build73 --probe-url https://VOTRE_SITE/hp-guard-probe.php --probe-file /var/www/VOTRE_SITE/hp-guard-probe.php
Application en maintenance (arrêt/redémarrage Apache) :
    sudo python3 tools/install_php73.py install --build /var/tmp/hp-guard-build73 --probe-url https://VOTRE_SITE/hp-guard-probe.php --probe-file /var/www/VOTRE_SITE/hp-guard-probe.php --apply
Retour arrière de cette installation :
    sudo python3 tools/install_php73.py rollback --transaction /var/backups/hp-guard/TRANSACTION --apply
Les étapes détaillées suivantes sont identiques pour 7.3, en remplaçant les noms
74/7.4 par 73/7.3 et le répertoire de build par hp-guard-build73.

1. RÉCUPÉRER ET CONSTRUIRE (EXEMPLE PHP 7.4)

    git clone https://github.com/sarlnsi/php-uploadprogress-guard.git
    cd php-uploadprogress-guard
    php7.4 -v
    phpize7.4 --version
    php-config7.4 --version
    python3 tools/build_php74.py --php /usr/bin/php7.4 --phpize /usr/bin/phpize7.4 --php-config /usr/bin/php-config7.4 --output /var/tmp/hp-guard-build

Compiler en compte non root. Le répertoire de sortie doit être nouveau.
Vérifications : version, NTS/non-debug, API 20190902, chargement CLI et glibc.
Résultat : hp_uploadprogress_guard.so, manifest.json, module-info.txt, build.log.
Les empreintes vérifient la cohérence du résultat, pas une signature d’éditeur.
Le checkout/script exécuté avec sudo et le build doivent être de confiance.

2. EXAMINER LE PLAN

Choisir un nouveau nom .php dans le DocumentRoot d’un backend précis. L’URL doit
arriver sur ce fichier local, sans répartition aléatoire entre serveurs ni
redirection. Le fichier ne doit pas déjà exister : il sera créé puis supprimé.
HTTPS vérifié requis ; HTTP autorisé uniquement sur loopback. Adapter les chemins :

    python3 tools/install_php74.py install --build /var/tmp/hp-guard-build --probe-url https://VOTRE_SITE/hp-guard-probe.php --probe-file /var/www/VOTRE_SITE/hp-guard-probe.php

Sans --apply : lecture du build et affichage du plan seulement. Aucun INI ou
service modifié, aucune requête envoyée. La compatibilité web sera contrôlée
lors de l’application. Le CLI peut être différent du PHP web.

Valeurs par défaut :
    --php /usr/bin/php7.4
    --ini-file /etc/php/7.4/apache2/conf.d/99-hp-guard.ini
    --web-group www-data

3. APPLIQUER SUR LE CLONE, PUIS EN MAINTENANCE

    sudo python3 tools/install_php74.py install --build /var/tmp/hp-guard-build --probe-url https://VOTRE_SITE/hp-guard-probe.php --probe-file /var/www/VOTRE_SITE/hp-guard-probe.php --apply

Cette commande arrête puis redémarre Apache ; les requêtes en cours peuvent
être interrompues. Elle requiert un Apache initialement actif et une configuration
valide. Elle crée une sonde avec un jeton aléatoire root:groupe-web 0640 dans
/run, distinct de tout PAT GitHub. Le jeton n’est pas copié dans le DocumentRoot.
Les contrôles n’utilisent que des GET administratifs : aucun exploit, upload,
OOM ou test de crash n’est envoyé au serveur.

Avant changement : contrôle de la version exacte du PHP NTS/non-debug servi, de son
module moteur chargé et de son ABI ; comparaison au build. Le profil strict
exige une limite mémoire finie et mbstring.encoding_translation désactivé.
Le script refuse ces écarts et ne modifie pas les autres atténuations existantes.
Une configuration de module déjà présente et étrangère n’est jamais écrasée.
Un ancien fork1 doit être retiré par retour arrière de sa transaction avant
installation du fork2 ; reconstruire avec cette révision, sans ancien manifeste.
Si open_basedir, /proc, le TLS ou les permissions bloquent la sonde, le contrôle
échoue : ne pas désactiver globalement vos protections pour forcer l’installation.

Sauvegardes et état : /var/backups/hp-guard/<transaction>/, root privé.
Le module est copié sous /opt/hp-guard/3.1.0-fork2/<empreinte>/.
Le nouvel INI contient :

    extension=/opt/hp-guard/3.1.0-fork2/<empreinte>/hp_uploadprogress_guard.so
    hp_uploadprogress_guard.mode=parse
    hp_uploadprogress_guard.detach_upload_progress=1
    hp_uploadprogress_guard.force_unlimited_memory=0

Le script ne remplace pas php.ini, ne rétablit pas automatiquement une limite
finie et ne modifie pas les autres modules/INI. Il conserve une archive des
configurations Apache/PHP existantes, un manifeste, l’état de transaction et les
journaux. Après arrêt d’Apache : création du seul INI, configtest, redémarrage,
contrôle HTTP des hooks et du SHA256 du .so effectivement chargé. Le reste des
extensions doit rester identique.

Résultat attendu : MITIGATION_INSTALLED_AND_OBSERVED, code 0.
Cela signifie « mitigation observée », pas « les deux CVE intégralement corrigées ».
La sonde et le jeton sont retirés en fin de commande, y compris après un échec
ordinaire. Une réexécution identique déjà observée évite un nouveau redémarrage.
Un moteur déjà corrigé peut mettre les hooks du module en retrait : le profil
strict ne doit pas être forcé dans ce cas ; vérifier la provenance du paquet.

Valider ensuite les parcours applicatifs normaux : authentification, sessions,
formulaires, uploads, traitements différés et erreurs. Ne pas lancer le script
lab_php73.py, lab_php74.py ou le module observer.c sur un serveur exposé.

4. ÉCHEC OU RETOUR ARRIÈRE

Un échec après le début du changement déclenche une tentative automatique de
retour arrière. Si elle réussit, l’INI créé est retiré et Apache redémarre dans
sa configuration précédente. Le code retour reste 1 pour signaler l’échec initial.
Si elle échoue, l’état devient rollback_failed et le script demande l’arrêt
d’Apache : vérifier son état et les journaux de la transaction avant intervention.

Le chemin de transaction est affiché avant l’arrêt d’Apache. Pour un retour
arrière manuel, examiner d’abord le plan (sudo permet de lire l’état privé ;
sans --apply aucun changement n’est effectué) :

    sudo python3 tools/install_php74.py rollback --transaction /var/backups/hp-guard/TRANSACTION
    sudo python3 tools/install_php74.py rollback --transaction /var/backups/hp-guard/TRANSACTION --apply

Cette commande retire seulement l’INI géré par cette transaction. Elle refuse
d’effacer une modification administrateur ultérieure. Les autres fichiers de
configuration ne sont pas restaurés aveuglément depuis l’archive. Le binaire
inactif et les sauvegardes sont conservés. Retirer la mitigation rétablit les
risques précédents si le moteur n’a pas reçu le correctif interne.

Une coupure système/SIGKILL rend la transaction non atomique. Utiliser son état,
les journaux et la sauvegarde pour une reprise manuelle ; une sonde temporaire,
un jeton ou un INI partiel peut devoir être examiné. Ne pas supprimer un fichier
dont l’origine ne correspond pas à cette transaction.

5. AUDIT ULTÉRIEUR FACULTATIF

L’installateur nettoie sa sonde. Pour une nouvelle vérification web, déployer
temporairement tools/runtime-probe.php dans le vhost et créer son jeton attendu :

    sudo python3 -c 'import os,secrets; p="/etc/php-cve-audit.token"; fd=os.open(p,os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o640); os.write(fd,(secrets.token_hex(32)+"\n").encode()); os.close(fd)'
    sudo chown root:www-data /etc/php-cve-audit.token
    sudo chmod 0640 /etc/php-cve-audit.token
    sudo install -m 0644 tools/runtime-probe.php /var/www/VOTRE_SITE/hp-guard-probe.php
    sudo python3 tools/check_runtime.py --url https://VOTRE_SITE/hp-guard-probe.php --token-file /etc/php-cve-audit.token --manifest /var/tmp/hp-guard-build/manifest.json

Adapter le groupe et les chemins. Ne pas écraser un fichier ou jeton existant.
Attendre MITIGATION_OBSERVEE_CORRECTIF_MOTEUR_NON_ATTESTE. Le code 2 indique un
profil non validé ou des preuves insuffisantes. Supprimer ensuite votre sonde et
le jeton. Répéter pour chaque backend ; un CLI seul n’atteste jamais Apache.

EFFETS DU MODULE
Un OOM intercepté termine le worker sans shutdown applicatif ; Apache le remplace
et la réponse courante peut être coupée. Des temporaires d’upload peuvent rester :
leur expiration relève d’une politique extérieure au chemin d’erreur. Le suivi
de progression des uploads par session est désactivé. Les limites du parseur
peuvent produire 413 avec abandon des données partielles.

Le rétroportage officiel reste la référence de remédiation des deux CVE.
